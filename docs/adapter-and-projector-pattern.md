# Adapter & Projector Layer Pattern

This document codifies how the **Adapter** (write-side I/O boundary) and **Projector** (read-side / CQRS query) layers are structured in OpportunityContext-style projects. Genesis generates the structural skeleton for both; this doc is the reference for what those skeletons should contain and why.

**Sources of truth:**
- swift-ddd-kit protocols: `swift-ddd-kit/Sources/DDDCore/*` and `swift-ddd-kit/Sources/EventSourcing/*`
- Generator behavior: `swift-ddd-kit/Sources/DomainEventGenerator/Generator/Model/AggregateRootGenerator.swift` + `ProjectorGenerator.swift`
- Reference impl: OpportunityContext `Sources/AuditQuotingAggregate/{Adapter,Usecase/Projector}/`

---

## 1. Where these layers live

Within a single aggregate target:

```
Sources/{Aggregate}Aggregate/
├── Usecase/
│   ├── Port/
│   │   ├── In/<UseCase>/                  # Write-side ports (Input/Output/Usecase)
│   │   └── Out/<Aggregate>Repository.swift
│   ├── Service/<UseCase>Service.swift     # Write-side use case impl
│   └── Projector/                         # ← READ-SIDE / PROJECTOR layer
│       └── Get<ReadModel>/
│           ├── <ReadModel>ReadModel.swift
│           └── Get<ReadModel>Presenter.swift
└── Adapter/                               # ← ADAPTER (I/O BOUNDARY) layer
    ├── ApiHandler.swift                   # Single OpenAPI conformance file per aggregate
    ├── ApiComponents/
    │   └── ApiComponents+<Type>.swift     # Domain ↔ OpenAPI component extensions
    ├── Dto/
    │   └── <Type>Dto.swift + <Type>Dto+Domain.swift
    └── <UseCase>/
        └── <UseCase>ApplicationService.swift
```

Plus, outside the aggregate target:

```
projections/
└── {Prefix}_Get{ReadModel}Projection.js   # KurrentDB-side projection script
```

**Key invariant**: the Adapter layer is the **only** outbound surface of an aggregate target. Other aggregates communicate via `DomainEventListener` in the context-level target (`Sources/{Context}/Listener/`), never by importing this aggregate's Adapter.

## 2. Adapter Layer

### 2.1 Responsibilities

The Adapter layer translates between the **domain language** (Aggregate, Command, DomainEvent, ContextError) and the **transport language** (OpenAPI request/response, DTO, HTTP status). It has four discrete concerns:

| Concern | File(s) | Generated by Genesis? |
|---|---|---|
| OpenAPI protocol conformance | `ApiHandler.swift` | Skeleton only (signatures from OpenAPI-generated stub) |
| Domain type ↔ OpenAPI component mapping | `ApiComponents/ApiComponents+*.swift` | Skeleton per domain enum/struct mentioned in OpenAPI |
| Cross-cutting DTOs | `Dto/*Dto.swift` + `*Dto+Domain.swift` | Per-DTO skeleton |
| Per-UseCase DTO + invocation | `<UseCase>/<UseCase>ApplicationService.swift` | Per-UseCase skeleton |

### 2.2 ApplicationService pattern (per UseCase)

Each write-side use case has **one** ApplicationService that:

1. Defines its own Input/Output **DTO** structs (distinct from `<UseCase>Input` / `<UseCase>Output` in the Port In layer — see §2.6)
2. Conforms to the `ApplicationService` protocol (from the Shared module, not from swift-ddd-kit)
3. Constructs the inner `<UseCase>Service`, executes it, then maps the Port In `Output` back to an outward DTO

Real OC shape (`AuditQuotingAggregate/Adapter/EditPaidInCapital/EditPaidInCapitalApplicationService.swift`):

```swift
import Foundation
import OCShared

package struct EditPaidInCapitalApplicationServiceInput {
    package let quotingId: String
    package let paidInCapital: Decimal
    package let operatorId: String
    package init(...) { ... }
}

package struct EditPaidInCapitalApplicationServiceOutput {
    package let quotingId: String
}

package struct EditPaidInCapitalApplicationService: ApplicationService {
    package typealias Input = EditPaidInCapitalApplicationServiceInput
    package typealias Output = EditPaidInCapitalApplicationServiceOutput

    private let repository: AuditQuotingRepository

    package init(repository: AuditQuotingRepository) { self.repository = repository }

    package func execute(input: Input) async throws -> Output {
        let service = EditPaidInCapitalService(repository: repository)
        _ = try await service.execute(input: .init(
            quotingId: input.quotingId,
            paidInCapital: input.paidInCapital,
            operatorId: input.operatorId
        ))
        return .init(quotingId: input.quotingId)
    }
}
```

**Why three structs not one** (per use case):
- `Input` / `Output` (Port In): pure domain types; tests use these directly
- `ApplicationServiceInput` / `ApplicationServiceOutput`: stable transport boundary; can absorb DTO changes without rippling into domain tests
- `Service` (Port In impl): pure domain logic

If the API contract changes (e.g., add a tracking ID, restructure the response), only the ApplicationService DTOs change. Domain logic and its tests stay unaffected.

### 2.3 ApiHandler pattern

OC keeps **one** `ApiHandler.swift` per aggregate at `Adapter/ApiHandler.swift` (singular file, not per-UseCase). It conforms to the `APIProtocol` generated by swift-openapi-generator from the aggregate's `openapi.yaml`.

Real OC shape (`AuditQuotingAggregate/Adapter/ApiHandler.swift`):

```swift
package struct ApiHandler<Storage: StorageProtocol & Sendable>: APIProtocol
    where Storage.MetadataType == StandardContextMetadata
{
    private let kdbClient: KurrentDBClient
    private let storage: Storage
    private var repository: AuditQuotingRepository {
        .init(coordinator: .init(client: kdbClient, eventMapper: AuditQuotingAggregateEventMapper()))
    }

    package init(kdbClient: KurrentDBClient, storage: Storage) { ... }

    private func mapToApiError(_ error: Error) -> Components.Schemas.AuditQuotingApiError? { ... }

    // One method per OpenAPI operation:
    package func getQuotingProofs(_ input: Operations.getQuotingProofs.Input) async throws
        -> Operations.getQuotingProofs.Output
    {
        let quotingId = input.path.quotingId
        let service = GetQuotingProofsApplicationService(kdbClient: kdbClient)
        let proofs = try await service.execute(input: .init(auditQuotingId: quotingId))
        // ... map to Operations.X.Output
    }
}
```

Each method follows the same shape:
1. Extract input from `Operations.X.Input` (OpenAPI-generated)
2. Construct an ApplicationService (write side) or Presenter/Projector (read side)
3. Execute, catch domain errors, map to HTTP error response via `mapToApiError`
4. Build `Operations.X.Output` from the result

**Storage is parameterized** (`Storage: StorageProtocol`) because file-handling use cases like `uploadQuotingProof` need to write to GCS/S3. For pure event-sourced aggregates without file I/O, the same pattern still applies with a no-op storage type.

### 2.4 ApiComponents pattern

For each domain type referenced in `openapi.yaml`, OC writes an `ApiComponents+<Type>.swift` file that adds an `init(from:)` initializer on the OpenAPI-generated `Components.Schemas.<Type>` to convert from the domain type.

Example file naming:
- `ApiComponents+AuditQuotingApiError.swift` — maps `ContextError<AuditQuotingError>` to API error component
- `ApiComponents+IndustrialType.swift` — maps domain enum to OpenAPI component schema

This isolates the transport mapping from the domain type itself (domain types never `import OpenAPIRuntime`).

### 2.5 Dto pattern

DTOs are types used **inside the Adapter layer** that don't fit cleanly into ApiComponents (e.g., shared across multiple endpoints, or used for richer projection input). Each DTO has two files:

- `<Type>Dto.swift` — the DTO struct itself (Codable, lives in Shared module level)
- `<Type>Dto+Domain.swift` — extension with `toDomain()` / `init(from domain:)` converters

This keeps the Codable DTO free of domain-type imports.

### 2.6 Three-layer Input/Output, summarized

| Layer | File location | Use |
|---|---|---|
| Port In | `Usecase/Port/In/<UC>/<UC>Input.swift` | Pure domain Sendable struct; conforms to `UseCaseInput` |
| ApplicationService DTO | `Adapter/<UC>/<UC>ApplicationService.swift` | Transport-stable DTO; ApiHandler builds this |
| OpenAPI operation | `Operations.<op>.Input` (generated) | swift-openapi-generator wire types |

Genesis generates **all three layers** but only the Port In + ApplicationService skeletons; ApiHandler bodies are filled per UseCase as those are added.

### 2.7 What Genesis generates vs leaves for the human

| Item | Genesis | Human/Skill |
|---|---|---|
| `<UC>/<UC>ApplicationService.swift` skeleton (Input/Output struct shells + `execute` calling Service) | ✅ | Body adjustments when DTO shape differs from Port In |
| `ApiHandler.swift` struct shell + storage generics + no methods | ✅ | One method per UseCase per `openapi.yaml` operation |
| `ApiComponents+<Type>.swift` per domain type mentioned in OpenAPI | Skeleton (init from domain) | Real mapping for enums/structs Genesis can't infer |
| `Dto/<Type>Dto.swift` | Not generated (per-feature; emerges only when needed) | Human writes as DTOs surface in spec |
| `openapi.yaml` paths | Not generated by Genesis | Human writes; swift-openapi-generator produces stubs |

## 3. Projector Layer

### 3.1 Responsibilities

The Projector layer implements the **read side of CQRS**: it materializes a `ReadModel` by replaying a subset of the aggregate's events. It has three concerns:

| Concern | File(s) | Generated by Genesis? |
|---|---|---|
| ReadModel type definition | `<ReadModel>ReadModel.swift` | Skeleton per `projection-model.yaml` entry |
| Per-UseCase projection logic | `Get<ReadModel>Presenter.swift` | Skeleton with `when` stubs per subscribed event |
| KurrentDB-side stream indexing | `projections/{Prefix}_Get<ReadModel>Projection.js` | Generated literally from template |

### 3.2 ReadModel pattern

Per swift-ddd-kit (`Sources/EventSourcing/Projector/ReadModel.swift`), the protocol is minimal:

```swift
public protocol ReadModel: Codable {
    associatedtype ID: Hashable
    var id: ID { get }
}
```

Real OC shape (`AuditQuotingAggregate/Usecase/Projector/GetPaidInCapital/PaidInCapitalReadModel.swift`):

```swift
import EventSourcing
import Foundation

package class PaidInCapitalReadModel: ReadModel {
    package var id: String { auditQuotingId }
    package var auditQuotingId: String
    package var paidInCapital: Decimal?

    package init(auditQuotingId: String) {
        self.auditQuotingId = auditQuotingId
    }
}
```

Conventions:
- `class` not `struct` — projector mutates this in place during `apply(readModel:events:)`
- `var id: { <aggregateRootIdField> }` — computed, points to a stored property
- Stored properties default to `Optional` because the read model may be queried before any state-bearing event has been replayed
- `package` access — read models never leak outside the aggregate target; ApplicationServices wrap them into DTOs

### 3.3 Presenter (Projector) pattern

The Presenter conforms to a generated protocol `Get<ReadModel>ProjectorProtocol` (produced by `ModelGeneratorPlugin` from `projection-model.yaml`). The protocol requires:

- `categoryRule` static var
- `buildReadModel(input:)` — build an empty/seeded `ReadModel` from the input ID
- `when(readModel:event:)` per subscribed event

Real OC shape (`AuditQuotingAggregate/Usecase/Projector/GetPaidInCapital/GetPaidInCapitalPresenter.swift`):

```swift
import DDDCore
import EventSourcing
import KurrentSupport

package struct GetPaidInCapitalInput: CQRSProjectorInput {
    package let id: String
    package init(auditQuotingId: String) { self.id = auditQuotingId }
}

package struct GetPaidInCapitalPresenter: GetPaidInCapitalProjectorProtocol {
    package typealias Input = GetPaidInCapitalInput
    package typealias StorageCoordinator = KurrentStorageCoordinator<Self>
    package typealias ReadModelType = PaidInCapitalReadModel

    package static var categoryRule: StreamCategoryRule { .fromClass(withPrefix: "OC_") }

    package var coordinator: KurrentStorageCoordinator<GetPaidInCapitalPresenter>

    package init(coordinator: KurrentStorageCoordinator<GetPaidInCapitalPresenter>) {
        self.coordinator = coordinator
    }

    package func buildReadModel(input: Input) throws -> PaidInCapitalReadModel? {
        return .init(auditQuotingId: input.id)
    }

    package func when(readModel: inout ReadModelType, event: PaidInCapitalEdited) throws {
        readModel.paidInCapital = event.paidInCapital
    }
}
```

Three things `ModelGeneratorPlugin` does for you so you don't have to write them:

1. **Protocol declaration**: `Get<ReadModel>ProjectorProtocol` is auto-generated from `projection-model.yaml`. You see it via the conformance, never by hand
2. **`apply(readModel:events:)`**: dispatches each event to the matching `when` you implement; default impl on the generated protocol
3. **`execute(input:)`**: fetches events → calls `buildReadModel` → calls `apply` → returns `CQRSProjectorOutput<ReadModelType>?`; default impl on `EventSourcingProjector` extension in swift-ddd-kit

You only write: `buildReadModel(input:)` and one `when(readModel:event:)` per subscribed event.

### 3.4 JS Projection pattern

KurrentDB-side projection. It listens to the source category stream and emits link events to per-aggregate-ID read-model streams.

Real OC shape (`projections/OC_GetPaidInCapitalProjection.js`):

```javascript
fromStreams(["$ce-OCAuditQuoting"])
.when({
    $init: function() { return {}; },
    PaidInCapitalEdited: handleEvent
});

function handleEvent(state, event) {
    if (event.isJson) {
        linkTo("OC_GetPaidInCapital-" + event.body["quotingId"], event);
    }
}
```

Naming convention:
- File: `{Prefix}_Get{ReadModel}Projection.js`
- Source stream: `$ce-{Prefix}{Aggregate}` (KurrentDB's `$ce-` prefix means "category index")
- Target stream: `{Prefix}_Get{ReadModel}-{aggregateRootIdField}`
- Per `event-generator-config.yaml` and `categoryRule` settings, the prefix must agree

The `EventSourcingProjector.fetchEvents(byId:)` reads from the **target** stream (`OC_GetPaidInCapital-<id>`), so this JS projection is the bridge between aggregate events and read-model queries.

### 3.5 What Genesis generates vs leaves for the human

| Item | Genesis | Human/Skill |
|---|---|---|
| `<ReadModel>ReadModel.swift` skeleton | ✅ (id field + one stored field per `projection-model.yaml` property) | Add stored fields as the read model grows |
| `Get<ReadModel>Presenter.swift` skeleton | ✅ (`buildReadModel` + `when(readModel:event:)` stub per subscribed event with `fatalError("not implemented")`) | Fill `when` bodies (projection logic) |
| `projection-model.yaml` entry | Not generated by Genesis | Human writes; declares subscribed events |
| `{Prefix}_Get<ReadModel>Projection.js` | ✅ (template render with Prefix + Aggregate + ReadModel + event list) | None — generation is deterministic |
| `Get<ReadModel>ProjectorProtocol` | Plugin-generated at `swift build` time | None — see §4 |

## 4. Plugin-generated code each layer depends on

Both layers depend on code that `DomainEventGeneratorPlugin` and `ModelGeneratorPlugin` emit at `swift build` time:

| Generated symbol | Plugin | Used by |
|---|---|---|
| `<EventName>` struct (Codable conforming to `DomainEvent`) | DomainEventGenerator | Command extension, ReadModel `when`, Presenter `when` |
| `<Aggregate>AggregateEventMapper` | ModelGenerator (`generated-event-mapper.swift`) | `<Aggregate>Repository.coordinator` initialization in ApiHandler |
| `<Aggregate>AggregateProtocol` | ModelGenerator (`generated-projection-model.swift`) | `<Aggregate>` class conformance |
| `Get<ReadModel>ProjectorProtocol` | ModelGenerator | `Get<ReadModel>Presenter` conformance |

These outputs live in `.build/plugins/outputs/.../generated-*.swift` and are linked into the target at compile time. Neither Genesis nor the human writes them.

**Required for plugin output**:
- Both plugins declared in target's `plugins:` list
- `event.yaml` + `projection-model.yaml` + `event-generator-config.yaml` declared as `resources` with `.process(...)`
- `event-generator-config.yaml` declares `accessModifier` (must match the access level the human writes for aggregate code; OC uses `package`)

## 5. Common pitfalls

1. **Forgetting `ApplicationService` DTOs as a separate layer** — flattening into Port In Input/Output couples API changes to domain tests. Keep three layers (§2.6).
2. **Using `struct` for `ReadModel`** — `apply(readModel:events:)` takes `inout`, but the projector's default `execute` uses `var readModel`, so struct works too. **However** OC uses `class` for consistency with `AggregateRoot` and to avoid copy-on-write surprises when the read model grows complex. Genesis defaults to `class`.
3. **Hard-coding the stream prefix** — the prefix (`OC_`, `IAM_`, etc.) must come from `event-generator-config.yaml`'s `streamCategoryPrefix` or `categoryRule`. JS projection naming, Swift `categoryRule`, and `<Aggregate>.category` must agree, or events written by the aggregate will not match the projection's source stream.
4. **`when(event:)` vs `when(readModel:event:)`** — the aggregate's `when(event:)` mutates aggregate state; the projector's `when(readModel:event:)` mutates a separately-typed ReadModel. They are NOT the same method, only conceptually paired.
5. **Importing another aggregate's Adapter** — forbidden. Cross-aggregate communication is `DomainEventListener` at the context level only.
6. **Wrong `aggregateRootIdField` in JS projection** — if the event payload uses `quotingId` but the JS does `event.body["auditQuotingId"]`, `linkTo` silently writes to the wrong stream and queries return nil. Genesis should derive this field name from `event.yaml`'s `aggregateRootId.alias`.
7. **Missing `fatalError` on Presenter skeleton** — Genesis must emit `fatalError("not implemented: when(readModel:event: \(eventType))")` not `// TODO`. The former fails loud at runtime if a downstream skill (or human) ships the file unfilled; a silent stub corrupts read models.

## 6. Genesis template responsibility summary

For each Aggregate + each ReadModel in the bundle, Genesis must emit:

**Adapter layer (per UseCase)**:
- `Adapter/<UC>/<UC>ApplicationService.swift` (single file)

**Adapter layer (per Aggregate, once)**:
- `Adapter/ApiHandler.swift` (struct shell, no methods)

**Adapter layer (per domain type mentioned in OpenAPI)**:
- `Adapter/ApiComponents/ApiComponents+<Type>.swift` (init-from-domain shell)

**Projector layer (per ReadModel)**:
- `Usecase/Projector/Get<ReadModel>/<ReadModel>ReadModel.swift`
- `Usecase/Projector/Get<ReadModel>/Get<ReadModel>Presenter.swift`
- `projections/{Prefix}_Get<ReadModel>Projection.js`

Genesis does **not** generate:
- `openapi.yaml` (human writes)
- `projection-model.yaml` (human writes)
- Method bodies that require business judgement (filled by `usecase` / `readmodel` skills downstream)

## 7. Open questions

1. **`ApiHandler` storage generic** — OC ties `Storage: StorageProtocol & Sendable` to FileStorageContext. For aggregates without file I/O, should Genesis emit a no-op `Storage` default, or skip the generic entirely?
2. **`ApiComponents` enum mapping** — for domain enums with `rawValue`, the mapping is mechanical; for sum types (Swift enums with associated values), it's not. Genesis should likely emit only `rawValue`-style enum mappings and leave structs/sum types as `fatalError("not implemented")` stubs.
3. **Per-ReadModel access modifier** — should follow `event-generator-config.yaml`'s `accessModifier`? OC uses `package` uniformly; Genesis should default to that and read from config for non-OC projects.
4. **`Dto/` folder generation policy** — OC creates DTOs ad-hoc when needed. Genesis should likely **not** auto-generate this folder; it emerges from per-feature spec writing.
